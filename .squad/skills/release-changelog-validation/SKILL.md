## When to use

- Bumping `package.json` for a preview, promote, or release branch
- Deciding whether `CHANGELOG.md` can be omitted or auto-generated by CI
- Preparing a small release where metadata consistency matters more than code changes

## Pattern

1. Update the package version in `package.json`.
2. Keep the root version in `npm-shrinkwrap.json` aligned when it is tracked.
3. Ensure `CHANGELOG.md` exists in-repo with a `## [<version>] - YYYY-MM-DD` heading for the new version.
4. Add a concise release note that accurately describes the shipped fix.
5. Validate with the repo's normal build command.

## PPTB Example

- `package.json` bumped from `1.0.4` to `1.0.5`
- `npm-shrinkwrap.json` version fields were updated to match
- Created `CHANGELOG.md` with a Keep a Changelog style `## [1.0.5] - 2026-06-05` entry for issue #74
- README developer guidance now notes that changelog maintenance happens in-repo

## Anti-Patterns

- **Assuming CI generates `CHANGELOG.md`** — this repo's workflows only validate the file; they do not create it.
- **Bumping only `package.json`** — tracked npm lock metadata can drift from the published package version.
- **Writing vague release notes** — changelog entries should identify the shipped fix clearly enough for preview and release review.
